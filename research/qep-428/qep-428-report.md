# QEP-428 分析报告：QGIS 全面禁止 AI 贡献

> 一手来源：qgis/QGIS-Enhancement-Proposals PR #387（2026-10-07 合并）、qgis-developer 邮件列表 2026-09 线程、QEP-408 原文 diff、后续 PR #388（QEP 429）。

---

## 一、讲了什么

**QEP-428 "No AI contributions permitted"** 是 QGIS（最大的开源 GIS 项目）的官方增强提案，2026-10-07 以社区投票通过并合并进 master，**取代**了之前宽松的 QEP-408 AI 工具政策。

### 核心条文（合并后的全文要点）

> "No LLM, AI or agent assisted code contributions are allowed in the qgis/qgis repository.
> If we subsequently discover that you have used an AI, LLM, or any agent-based workflow for your contribution, you will be subject to code reversion and contributor rights sanctioning."

- **全面禁止** LLM / AI / agent 辅助的代码贡献进入 `qgis/qgis` 仓库；事后发现将**回滚代码 + 制裁贡献者权利**（可临时或永久封禁）。
- 这份 diff 最能说明态度：它把 QEP-408 那份 130 余行、借鉴 LLVM "AI Tool Use Policy" 的精细政策（human-in-the-loop、`Assisted-by:` trailer 声明、"extractive contribution" 概念、违规处理流程、版权条款）**整段删除**，只剩两句禁令。版本号升到 2.0，作者改署 "the QGIS project contributors"。
- **范围**（据 PR/邮件讨论）不止代码：issue、QEP、文档、PR 描述、GitHub 上的一切书面交互都在内；QEP 仓库本身也覆盖。
- **执行方式**是自觉原则——PSC 主席 Tim Sutton 原话："合规标准就是'你是否凭良心亲手写了这段代码'，我们没有能力窥探你的电脑。"
- **明确的后续意图**：先"把门关死"，再逐案放开个别场景（如 IDE 补全、翻译辅助）。Nyall Dawson："我们清楚这可能把孩子和洗澡水一起倒掉，但这个孩子可能本来就是死胎。"

### 社区反应

- 支持方（含一位提交过 AI 辅助修复的贡献者 Amalvir）："AI 贡献打破了评审者与贡献者之间的信任契约——你要向大项目贡献，前提是你知道自己在干什么。"
- 反对方（开发者 Kannes 等）：条文中 "assisted"、"used" 措辞太宽，会误伤用 AI 做代码评审、安全审计、学习陌生代码库的正当用法。
- 主力提案人 Even Rouault（QEP-408 作者）已处于 "on strike" 状态；他对 QEP 429 的评价："这个提案不如改名叫'成分不明的毒品只允许成年人使用'。"
- daily.dev 社区民调：20% 支持 / 45% 中立 / 35% 质疑。Hacker News 讨论 300+ 条。
- 批评焦点之一：这是"Level 0 控制"——一段没人执行的英文，触发条件（"这段代码是 AI 写的吗"）只有良心能评估，注定无法落地检测。

## 二、为什么这么做

1. **维护者过载是真实危机**。PSC 成员 Julien Cabieces："外部贡献者的 AI 使用把巨大且难以承受的压力压在维护者身上……AI 流量远超人类评审能认真消化的上限，结果要么是未评审 PR 越积越多，要么是没审透的代码引入质量问题。"
2. **轻量治理已被证伪**。QEP-408 只要求"人工把关 + Assisted-by 声明"。实际结果：约 50 个 PR 打了 "AI Assisted" 标签，约 40 个被关闭未合并，还有不打标签的漏网。Dawson："那个流程在现实中根本没发生。"
3. **付出的代价已经不可逆**：项目**至少流失了一位极高价值贡献者**。
4. **信任契约崩塌**：sloppy 的 AI PR 让评审变成"替别人验证 LLM 输出"，把成本从提交者转移给维护者——即 QEP-408 借自 Nadia Eghbal《Working in Public》的 "extractive contribution"（榨取式贡献）问题恶化到失控。
5. **版权/CLA 隐患**：早在 QEP-408 讨论期就有人指出，接受 LLM 输出与"贡献者须有权按项目许可证授权代码"的要求冲突。后续拟引入 CLA 签署流程。
6. **先关后开的策略选择**：项目认为"现在宽松、将来收紧"的社会成本远高于"现在严格、将来逐案放开"。禁令是止血，不是终局。
7. **大环境**：Linux 内核 2024 年就警告过 AI 补丁浪费维护者时间，但只是非正式劝告；QGIS 是第一个把禁令写成**正式项目政策**的头部开源项目。

## 三、对我们有什么影响

**1. 向 QGIS 及其生态贡献的路径变了。**
- 任何面向 `qgis/qgis` 的 PR/issue/文档/评论都不能出自 AI 工作流，被发现即回滚+制裁。插件生态目前不在禁令内（官方立场：插件作者自负其责），但社区已有人要求对插件更严（插件走的是 QGIS 插件仓库、审查更松、有安全风险）。
- 如果我们有基于 QGIS 的产品、二次开发或外包交付，上游贡献流程需要人工重做或走内部 AI 辅助 + 人工全权重写的边界管理。

**2. 依赖 QGIS 的工程实践受影响。**
- 上游合并节奏可能因评审人力紧张而变慢（禁令本来就是为了保护评审带宽）；QEP 429 若通过，会出现"老贡献者可用 AI、新人不可"的双轨制，影响我们新人参与上游的路径设计。

**3. 风向标效应。**
- QGIS 是第一个明文立法的头部项目。OSGeo 系（GDAL 由同一核心开发者 Rouault 维护）、其他基金会（Apache/CNCF/Eclipse 等）大概率跟进或引用此先例。给上游开源项目的贡献合规会逐渐成为供应链尽调的一部分。
- 反过来，"无 AI 贡献"可能成为开源项目的**质量信号/卖点**，影响选型时的信任判断。

**4. 对我们自己使用 AI 编码（比如本仓库这种 agent 工作流）的合规含义。**
- **内部代码**不受影响，但一旦代码流向受管制的上游，AI 溯源就成了硬边界。需要能回答"这段代码有没有进过 AI 工作流"——即提交物级别的溯源能力，而不只是最后一步的"我检查过了"。

## 四、我们能学到什么

1. **"人工把关 + 自愿声明"这类轻量政策会失败**。QEP-408 的设计并不差（LLVM 同款、有标签、有流程），失败在于触发依赖自觉、没有机器强制、违规无成本。给团队定 AI 使用规范时，凡是靠"记得申报"的条款，默认按失效设计。
2. **规则的可评估性比严格性更重要**。QEP-428 的措辞争议（"assisted" 太宽）正是因为它把不可判定的触发条件写成了硬规则。我们内部定规则应优先定义**可判定的边界**（例如：进入 X 仓库的 diff 必须带 Y 声明字段），而不是"禁止 AI 参与"。
3. **先关门、再逐案放开优于先放开、再收紧**。Dawson 的策略本质是可逆性管理：严格政策的放松成本低，宽松政策的收紧成本高（要先付出流失贡献者的代价才知道错了）。
4. **保护评审者的注意力是第一优先级**。QGIS 的黄金法则仍然有效："一个贡献的价值必须大于评审它的时间。" 无论政策怎么写，内部评审带宽预算是真实约束——AI 把实现成本降到近零之后，评审成为唯一稀缺资源，流程设计应围绕它。
5. **信任是有层级的，不要一刀切在错的层**。QEP 429 的分裂说明：社区真正在争的不是"AI 好不好"，而是"谁有资格用"。如果我们做分级（如资深工程师可用 agent 自主提交、新人必须人工逐步走），应在制度里显式写出分级依据，否则会重演这场争论。
6. **署名与溯源 > 检测**。"检测 AI 代码"是不可赢的对抗问题；赢不了检测，就做**收据（receipt）**：谁署名、承诺了什么、经过谁审。这与 QGIS 的"良心原则 + 事后制裁"其实同构——差别只在是否留痕。我们的提交流程应默认携带人工署名与 AI 参与声明（哪怕只是内部 trailer）。
7. **政策文本要短、只写 what**。Tim Sutton 特意要求删掉 rationale 和嘲讽彩蛋："写 why 会把我们拖进无休止的细节争论。" 这条对任何工程规范文档都成立：动机写在附录或 FAQ，正文只写规则。
8. **社区共识管理也是工程问题**。QGIS 的处理堪称教科书：邮件列表酝酿 → PSC 表态但让出流程 → 正式 QEP 投票 → 允许后续 QEP 修正（429）。即使政策激进，程序正义让反对者留在了社区里（反对票被记录、例外通道被保留）。

## 五、风险与开放问题（值得跟踪）

- **可执行性**：禁令靠自觉 + 事后制裁，误伤与漏网都会发生；"Level 0 控制"的批评尚未被回应。
- **QEP 429 的走向**：若通过，形成可信/不可信双轨；若否决，激进派与实用派的裂痕持续。
- **边界案例**：翻译、拼写检查、AI 辅助代码评审、AI 总结陌生代码库是否算违规，官方未定。
- **法律层面**：版权/CLA 条款尚未落地；"AI 生成代码的许可证合规"仍是全行业未解问题。
- **生态外溢**：插件仓库、文档站、下游发行版是否跟进，尚不明确。
